Where the configuration lives

Everything this view remembers — expand state, custom icons, node tooltips, hidden nodes and the module toggle — is stored in two YAML files inside the opened project. Click a path to open it.

Team default    {{defaultFileShort}}
Checked into version control, never overwritten by the plugin.
Personal overrides    {{customFileShort}}
Written automatically, takes precedence, and records only what deviates from the default.
Icons    {{iconsDirShort}}
Image files referenced by name from either YAML file.

The toolbar's Reset to Default deletes the personal file, so the team default applies again. Hand edits to either file are picked up on the next refresh, and Settings > Reload applies them — and newly added icon files — right away. Neither needs an IDE restart.

Shape of a file

The top level has exactly four keys. Group paths and task names live in separate namespaces, so a task called build and a group called build never affect each other.

What a node entry may contain

expanded    Expand state. A bare true/false instead of a mapping is the short form for exactly this field.
icon    File name relative to the icons directory. A sibling <name>_dark.<ext> is preferred automatically under dark themes. A missing file falls back to the built-in icon and logs a warning.
description    Tooltip of a module, group or folder node. Without it, those nodes have no tooltip at all. Tasks ignore it and keep showing their Gradle description. The text is written once for every view mode, so it is not read inside modes.
hidden    Hides the node. The only field inherited along a path: a hidden folder takes its whole subtree with it, and a more precise entry can take it back.
execute    Only inside the tasks of a group entry: turns that entry into a row of its own that runs the referenced Gradle task. See below.
tasks    Only in a group entry: the nodes that appear in this group in addition to the tasks Gradle puts there.
modes    The same fields again — except description — but only for default, sort or nested.

Nodes you define yourself

An entry inside the tasks of a group that carries execute becomes its own row in the tree. It creates no Gradle task — it runs the one execute points at, so double-click, Run, Debug and Run with Coverage all work as usual — see the docker/test entry in the example above: it adds a row testDocker that runs printLibGui, in a group that exists nowhere else.

The name    Is yours. It does not have to exist as a Gradle task, and it is what the tree shows and the search matches.
The group    Does not have to exist either. Groups exist only because nodes carry their path, so the entry above creates ci/nightly — nested paths and all.
execute    Qualified (":app:buildImage") means exactly that module; a bare name ("buildImage") means every module that has such a task. Use the path as this view shows it — Copy Task Path on the task gives you exactly the right string. A reference that resolves to nothing produces no row and logs a warning naming the paths the task does have.
Hiding    Such a node is addressed by its entry, not by the task it runs: hiding that task removes it from its original place only, and the node stays. It is hidden through its own hidden — or with the group or module it sits in.

Which entry wins

Resolved per node and per field, in this order:

  • module-scoped before module-independent,
  • mode-specific before all-modes,
  • personal file before team default,
  • then the built-in default (expanded, plugin icon, no tooltip, visible).

hidden uses the same order with one criterion in front: how precisely the entry names the node — task, then folders from the inside out, then module.

Folder paths are the slash-separated group paths shown in the tree (docker/server/gui). A folder that is compacted into one row keeps its full path as the key, so an entry for a compacted-away intermediate node has no effect. The Tasks node of the Default view has no key at all and follows its module.
